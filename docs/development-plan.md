# RxPlayer 分阶段开发计划

- 版本：v0.1 规划基线
- 更新日期：2026-10-28
- 需求依据：[总需求](requirements.md)

统一进度入口：[当前进度](progress.md)。阶段开始、任务完成、阻塞或验收结果变化时同步更新，不把规划项当成已完成功能。

## 1. 目标与执行原则

目标是先交付能在 Windows 和 Android 上稳定收听三个音源的首版，再扩展音乐库和辅助体验。Material 3 Expressive 在每个阶段持续验收，不放到最后统一换皮。

本文件是总开发路线，不是一次性实现全部系统的代码清单。进入一个阶段时，再针对已选定能力编写具体文件、接口、验证方式和交付范围，避免提前设计尚无证据支持的框架。

按当前用户约定，默认不自动运行构建；只有用户明确要求构建 / 启动 / 构建验证时才执行对应操作。阶段验收所需但尚未获授权执行的项目保持“未验收”，不得根据静态检查勾选通过。本次文档工作不额外构建或操作设备。

计划顺序是建议，未承诺日历工期。先消除音源可用性和 Windows 流媒体引擎的不确定性，再根据实际进展估算。

## 4. M1：设计基线与技术可行性

### 4.1 修订信息架构与 Expressive 设计

涉及现有文件：

- `composeApp/src/commonMain/kotlin/com/keno/rxplayer/App.kt`：页面组织、导航和自适应布局。
- `composeApp/src/commonMain/kotlin/com/keno/rxplayer/ui/Theme.kt`：颜色、排版、形状和动效。
- `composeApp/src/commonMain/kotlin/com/keno/rxplayer/ui/Player.kt`：状态表达、迷你 / 展开播放器。
- `composeApp/src/commonMain/kotlin/com/keno/rxplayer/ui/Artwork.kt`：封面裁剪与嵌套圆角。

任务与交付：

- [ ] 以“搜索、音乐库、设置”的建议结构完成页面规格；播放页和队列作为任务面板。
- [ ] 对照 m3-expressive 参考，确定导航组件、选中图标和颜色角色；不以增加空入口凑组件数量。
- [ ] 统一准备、播放、暂停、结束和错误的文案、图标、时长显示与可用操作。
- [ ] 收敛欢迎卡片的视觉权重，把搜索和播放作为主任务。
- [ ] 调整嵌套圆角和排版层级，记录偏离标准 token 的产品设计理由。
- [ ] 定义各窗口范围的导航与辅助面板行为，保留音乐库位置和当前播放任务。
- [ ] 补齐空格、Tab、Esc、悬停提示、无障碍标签及放大文字后的布局方案。

产物：一份可直接实施的页面规格、双端关键状态截图，以及 UI-01～08 对照清单。数字 token 与实际 API 分别核对，不因技能描述某 API 就假设工程当前版本已经具备。

### 4.2 验证三个音源与 Windows 引擎

- [ ] 对每个音源分别验证关键词搜索、内容标识、音频解析、格式、请求头、链接有效期、匿名 / 登录边界。
- [ ] 对 YouTube 单独记录普通视频和 YouTube Music 能力；不能只记录后者后宣称完成前者。
- [ ] 确定必要的登录方式和本地凭据保存方式，记录过期 / 退出流程。
- [ ] 选择 Windows 可分发的流媒体引擎，验证真实返回格式、HTTPS 请求、鉴权请求头、暂停继续、拖动与资源释放。
- [ ] 输出音源能力矩阵、流媒体引擎选型记录和可重复的样本；记录不可用能力及原因。

退出条件：三来源的 P0 路径均有可行证据，或阻断条件已经明确反馈并形成需求调整。若某个来源不成立，不静默删掉该来源，也不先构建依赖它的大量页面。

## 5. M2：Bilibili 与通用播放基础

先以一个真实来源跑通完整链路，再扩展来源数量。涉及共享层、现有 `audio/` 状态与适配，以及双端平台入口；拆分代码只服务本阶段实际职责。

- [ ] 实现 B 站关键词搜索、分页、视频链接 / BV / AV 识别与分 P 选择。
- [ ] 用统一内容模型承载来源、ID、标题、作者、封面、时长及分 P，不再用 `DemoTrack` 承载真实内容。
- [ ] 在真实搜索入口替换演示数据，保留独立演示资源用于回归检查。
- [ ] 将现有只接收 WAV 字节的播放接口演进为流媒体播放；接入已验证的 Windows 引擎和 Android 播放服务。
- [ ] 实现统一队列、添加 / 移除 / 排序、播放模式、缓冲、错误与有边界的恢复。
- [ ] 实现本地数据库和设置持久化，完成收藏、歌单、最近播放、队列及位置恢复。
- [ ] Android 接入后台播放、媒体会话、通知 / 锁屏、音频焦点和耳机事件。
- [ ] Windows 接入最小化继续播放、系统媒体控制、媒体键、托盘与明确退出行为。
- [ ] 完成本地搜索空结果、网络错误、内容下架、账号要求等状态。
- [ ] 按 M1 页面规格实现并复核 Expressive 体验。

验收样本：普通视频、多分 P、长标题、不可用内容、需要登录内容、过期链接，以及快速切换和断网恢复。两端必须都能完成“搜索 → 选择内容 → 播放 → 入队 → 收藏 → 重启恢复”。

本阶段可以交付 B 站预览版，但版本说明必须明确其余来源未完成。

## 6. M3：网易云接入

- [ ] 实现网易云歌曲搜索、分页、元数据和歌曲链接解析。
- [ ] 区分可完整播放、试听、无权限、下架与请求失败，不把全部结果显示为可完整播放。
- [ ] 实现必要登录、登录失效和退出清理；保持匿名可用能力可独立访问。
- [ ] 将网易云曲目接入现有队列、收藏、歌单和历史，不另建一套播放器状态。
- [ ] 处理原平台允许的音质和播放资源，失效时重新解析当前来源。
- [ ] 双端验证 B 站与网易云混合队列，重启后内容身份与来源保持正确。

退出条件：SRC-01、相关账号要求及混合队列通过双端验收。歌词、歌单读取和跨源自动匹配不作为本阶段隐含交付项。

## 7. M4：YouTube 接入

- [ ] 实现已在 M1 验证的普通视频关键词搜索、分页和常见视频链接识别。
- [ ] 独立标识 YouTube Music 目录及其附加能力，避免两者范围混淆。
- [ ] 接入可用音频解析、格式、请求头和会话信息，验证拖动、过期及重新解析。
- [ ] 对匿名、登录、地区、网络、内容权限和平台校验失败分别给出状态。
- [ ] 将来源内容接入同一队列和本地音乐库，避免同名内容被错误合并。
- [ ] 双端完成 Bilibili、网易云、YouTube 三源混合队列及恢复验证。

退出条件：SRC-03、相关账号要求和三源播放成立。遇到阻断先交付可复现记录，再讨论范围或方案调整，不将未验证能力写成已支持。

## 9. M6：首版之后

按实际反馈一次选择一项扩展，不整包同时开展：

1. 平台歌单 / 收藏夹只读接入与本地歌单导入导出。
2. 歌词、歌词匹配和显示体验。
3. 缓存容量、音频输出等播放设置。
4. 经用户明确纳入范围的下载、同步、平台写入或一起听。

涉及远端写操作或公共服务的能力，先写清账号、数据、冲突处理和运行成本，再进入具体实现。

## 11. 阶段完成的证据

每个阶段的验收记录至少包含：代码版本、操作系统 / 设备 / 窗口条件、实际执行的命令或步骤、预期和实际结果、关键截图、失败项及未执行项。

新功能默认使用覆盖完整功能或阶段的 `codex/<feature>` 分支，避免按细小任务拆分。当前授权任务达到相应验收条件后，直接提交并推送，再合并主分支并推送；具体规则以仓库 AGENTS.md 为准。

- 有代码：记录“已实现”，不自动记为“已验证”。
- 构建成功：只证明对应目标能编译打包。
- 启动成功：只证明当时窗口 / Activity 可以进入。
- 完成交互与异常场景：才可关闭对应验收项。
- 只修改文档：检查链接、需求覆盖、阶段依赖与 Git 差异，不额外构建应用。

下一项建议工作：M0 剩余检查和 M1 的页面规格 / 可行性验证。当前仅完成规划文档，不在本次直接修界面或接音源。
